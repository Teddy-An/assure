# Assure

**테스트 통과를 넘어, 제품 전체의 릴리스 준비 상태를 검증합니다.**

Assure는 Codex가 프로젝트의 기능과 사용자 시나리오를 파악하고, 실제
코드에 정상값·실패값·경계값을 넣어 동작시키며, 운영 부작용 없이 제품
전체의 릴리스 준비 상태를 판정하도록 만드는 플러그인입니다.

[English](README.en.md) | **한국어**

> **Early beta:** 현재 사용할 수 있지만 manifest 형식과 설치 방식은
> 변경될 수 있습니다.

## 왜 Assure가 필요한가

테스트 runner는 **등록된 테스트가 통과했는가**를 알려줍니다.

하지만 릴리스 전에 필요한 질문은 더 큽니다.

- 제품의 주요 기능과 사용자 흐름이 모두 검증 대상에 들어갔는가?
- 테스트가 없는 기능은 무엇인가?
- 현재 테스트가 지금 코드와 여전히 연결되는가?
- 자동화할 수 없는 항목은 누가 확인해야 하는가?
- 실패와 미확인 항목의 위험도를 고려할 때 지금 릴리스해도 되는가?

Assure는 이 질문을 프로젝트 전체 범위에서 반복 가능한 검증 기준으로
관리합니다.

```text
환경 조사 → 공통 Sandbox 구성 → 기능·입출력·부작용 파악
         → 모든 기능의 Assure probe 생성 → 격리 실행 → 릴리스 판정
```

## 무엇이 다른가

| | 일반 테스트 runner | 일회성 에이전트 검증 | Assure |
|---|---|---|---|
| 출발점 | 이미 작성된 테스트 | 현재 요청과 대화 | 제품 기능과 사용자 시나리오 |
| 검증 범위 | 실행한 테스트 | 에이전트가 선택한 범위 | 등록된 전체 기준 |
| 빠진 검증 | 알 수 없음 | 놓칠 수 있음 | 자체 기능 probe로 우선 실행 |
| 수동 확인 | 별도 관리 | 대화에 남음 | 기준과 결과에 포함 |
| 변경 추적 | 테스트 결과 중심 | 세션이 끝나면 소실 | Git과 source snapshot으로 추적 |
| 실행 안전성 | 호스트 환경에 의존 | 작업 방식에 따라 다름 | 원본과 분리된 임시 복사본 |
| 외부 시스템 | 실제 연결 또는 별도 환경 필요 | 작업 방식에 따라 다름 | 지원 경계는 메모리 대체, 나머지는 실행 거부 |
| 최종 결과 | pass/fail | 설명 또는 수정 결과 | 위험도 기반 릴리스 판정 |

Assure는 Vitest, Jest, pytest 같은 기존 runner는 활용하지만 프로젝트가
원래 가지고 있던 테스트를 릴리스 증거로 직접 실행하지 않습니다. 기존
테스트는 기대 동작을 이해하는 참고 자료일 뿐입니다. 모든 자동 시나리오에
대해 실제 제품 코드를 호출하는 Assure 소유의 기능 probe를 만들고, 외부 DB·인증·결제·메시지
경계는 지원되는 통제된 메모리 대체물로 바꿔 결과와 부작용을 함께
검증하며, 안전하게 대체할 수 없는 경계는 실행하지 않습니다.

## 핵심 원칙

1. **운영 소스 무변경**: 원본 작업 트리와 운영 코드를 수정하지 않습니다.
2. **운영 데이터 무접촉**: 운영 DB, 저장소, 계정의 데이터를 읽거나 쓰지
   않습니다.
3. **운영 서비스 무호출**: 운영 인증, 결제, 메시지, 외부 API에 요청을
   보내지 않습니다.
4. **자체 실행 가능**: Docker, Podman, Emulator, 브라우저 driver가 없어도
   지원되는 OS 격리 provider와 Assure 기능 probe로 검증합니다. 보조
   도구가 안전하게 사용 가능하면 격리 강도와 증거의 현실성을 높이는
   provider로 우선 활용합니다. 컨테이너와 지원 OS 격리가 모두 없으면
   안전 원칙을 낮추지 않고 자동 실행을 `미검증`으로 종료합니다.
5. **토큰과 작업 시간 최소화**: 검증 신뢰도와 전체 범위를 희생하지 않는
   선에서 결정적 수집기를 먼저 사용하고, 필요한 소스와 증거만 읽으며,
   동일한 명령·분석·보고를 반복하지 않습니다.
6. **기능에서 코드로 역추적**: 전체 소스 본문을 순서대로 읽지 않습니다.
   전체 인벤토리에서 기능과 사용자 시나리오를 세운 뒤, 각 시나리오의
   진입점, 상태 변화, 권한 경계와 외부 효과에 필요한 코드만 역방향으로
   추적합니다. 결정적 수집기는 변경 감지를 위해 전체 후보 파일의 경로와
   해시를 계산할 수 있지만, 그 본문을 모델의 토큰 컨텍스트로 보내지는
   않습니다.
7. **실행 증거 우선**: 정적 분석은 검증 설계에 사용하되, 실제 동작을
   실행하지 않고 통과로 판정하지 않습니다.
8. **결과와 부작용 동시 검증**: 기대 결과뿐 아니라 필요한 쓰기가 정확한
   횟수로 발생했는지, 금지된 쓰기나 호출이 없었는지도 확인합니다.
9. **정직한 판정**: 검증할 수 없는 항목은 근거와 시도 내역을 남기며,
   통과로 꾸미지 않습니다. 사람의 판단은 물리적·시각적·법적·동의가
   필요한 경우로 제한합니다.
10. **전체 기준 회귀검증**: 변경된 파일만 검사하지 않고 승인된 전체 기능
   기준을 실행해 다른 기능에 생긴 영향까지 판정합니다.
11. **준비 우선·일괄 승인**: 시나리오 실행 전에 격리 권한과 러너 준비를
   점검합니다. 기술 스택, 최소 Sandbox 구조, 생성 파일과 필요한 의존성
   전체를 한 번에 보여주고 한 번만 승인받습니다. 승인 후에는 승인 범위
   전체를 자동 준비하며 항목마다 다시 묻지 않고, 계획 해시·승인자·시각을
   증거로 남깁니다. 승인 전에는 시나리오를 실행하지 않습니다.
   이 계획을 거절하면 테스트를 시작하지 않고 예상 미검증 범위만 보고합니다.

### 다른 워크플로와의 격리

Assure가 실행되는 동안에는 Assure, Assure Map, Assure Verify만 사용합니다.
대상 저장소의 문서는 제품 제약조건을 파악하는 데 참고할 수 있지만, 그
안에서 추천하는 외부 스킬, 에이전트, MCP, 계획·디버깅·정밀 소스 분석
절차를 Assure 흐름에 추가하지 않습니다.

시스템·개발자·사용자 또는 프로젝트의 상위 지침이 외부 워크플로 사용을
반드시 요구하면 Assure가 그 지침을 무시할 수는 없습니다. 이 경우 두
워크플로를 섞지 않고 Assure를 중단해 지침 충돌을 보고합니다.

저장소 루트의 `AGENTS.md`와 `CLAUDE.md`는 Assure 자체를 개발할 때
원칙이 변질되지 않도록 보호합니다. 대상 프로젝트에는 이 파일들을
생성하지 않습니다. 그런 파일은 프로젝트 전체에 영향을 주며, 설치된
플러그인의 실행 격리를 보장하는 수단이 아니기 때문입니다.

### 원칙의 강제 수준

| 수준 | 적용 항목 |
|---|---|
| 코드로 강제 | 임시 복사본, 원본 읽기·쓰기 차단, 자격증명 제거, OS 네트워크 차단, 실행 전 권한 preflight, 승인 없는 의존성 준비 중단, runner allowlist, 외부 경계 fail-closed, probe 해시, 전체 기준 실행, 결과 판정 |
| 스킬 절차로 강제 | 준비 작업의 대상·이유·영향 고지와 사용자 승인, 기능에서 코드로 역추적, 모든 시나리오의 자체 probe 생성, 토큰·중복 작업 최소화 |
| 상위 지침 경계 | 시스템·개발자·사용자·프로젝트 지침과 충돌하면 Assure 중단 및 충돌 보고 |

스킬 절차만으로 안전을 보장하지 않습니다. 운영 영향과 기준 무결성에
관련된 항목은 결정적 스크립트가 다시 검사하며, 스크립트가 보장할 수 없는
항목은 통과가 아니라 `미검증`으로 처리합니다.

## 검증 흐름

```text
사용자 요청
└─ Assure 상태 확인
   ├─ 승인 기준이 최신임 ───────────────────────────────┐
   └─ 기준 없음·손상·변경됨                             │
      └─ 프로젝트 인벤토리 수집                         │
         ├─ 기술 스택·라우트·스키마·테스트 관계         │
         └─ 전체 소스 본문을 일괄 정독하지 않음         │
            └─ 기능 구조 생성                           │
               └─ 기능                                  │
                  └─ 사용자 시나리오                    │
                     └─ 필요한 코드 경로 역추적         │
                        ├─ 실제 진입점                   │
                        ├─ 허용·거부 조건                │
                        ├─ 상태 변화                     │
                        ├─ 권한 경계                     │
                        └─ 외부 효과                     │
                           │                             │
                           └─ 기존 테스트는 참고만 함    │
                              └─ 최초 승인된 Sandbox 계획 적용
                                    └─ Assure 기능 probe 생성
                                 ├─ 정상 입력
                                 ├─ 실패 입력
                                 ├─ 경계 입력
                                 ├─ 실제 제품 코드 실행
                                 └─ 위험한 외부 경계만
                                    fake·spy로 대체
                                       ├─ 결과·상태 검증
                                       ├─ 필요한 효과 검증
                                       └─ 금지된 효과 검증
                                             │
                              ┌──────────────┘
                              └─ probe 정책 검사
                                 ├─ 파일·진입점·SHA-256 일치
                                 ├─ 정상·실패·경계 사례
                                 ├─ 결과·부작용 assertion
                                 └─ 미검증이면 시도·사유 기록
                                    └─ 기준·snapshot 자동 기록
                                                       │
   ┌───────────────────────────────────────────────────┘
   └─ 실행 준비 점검
      ├─ 내부 임시 경로 쓰기·삭제
      ├─ 외부 쓰기·네트워크 차단
      ├─ runner·의존성·권한 확인
      └─ 다운로드·설치·생성 필요
         ├─ 없음 → 계속
         └─ 있음 → 최초 Sandbox 계획에 포함
                    └─ 이미 승인됨 → 자동 준비
   └─ 승인된 전체 시나리오 실행
      └─ 실행 provider 선택
         ├─ Docker·Podman 사용 가능 → 더 강한 격리
         └─ 보조 도구 없음
            ├─ 지원 OS 격리 → Assure local-isolated
            └─ OS 격리 없음 → 실행 거부·미검증
               └─ 원본·운영 자격증명·운영 네트워크와 분리
               └─ 시나리오별 증거 수집
                  ├─ 통과
                  ├─ 실패
                  ├─ 확인
                  ├─ 미검증
                  └─ 제외
                     └─ 기능 구조 + 전체 결과표
                        └─ 릴리스 판정
                           ├─ releasable
                           ├─ blocked
                           └─ warning
```

## 한 번의 요청으로 하는 일

Codex에서 다음과 같이 요청합니다.

```text
이 프로젝트를 Assure로 전체 검증해줘.
```

Assure는 프로젝트 상태에 따라 필요한 과정을 이어가되, 새 파일·의존성·
권한을 포함한 전체 준비 작업을 최초 Sandbox 계획에서 한 번만 승인받습니다.
Assure는 실행 전에 프로젝트 기술 스택, 테스트 러너, 격리 제공자,
`.assure` 쓰기 권한과 시나리오별 실행 능력을 먼저 점검합니다. 관리자 권한을
일괄 요구하지 않으며, 실제 필수 작업에서 권한 부족이 확인된 경우에만 정확한
대상과 이유를 제시합니다.

React DOM처럼 실제 제품 로직 실행에 필요한 최소 실행 능력은 승인 후 원본
`package.json`이나 lockfile을 바꾸지 않고 `.assure/capabilities`에 잠긴
오버레이를 생성해 임시 복사본에만 적용합니다. 고정 설치법이 없는
환경은 사용자의 LLM이 프로젝트별 준비 계획과 Adapter를 생성하고 건강검사를
통과시킵니다. Assure의 내장 설치법이 없다는 이유만으로 미검증 처리하지 않습니다.
Firestore를 포함한 외부 저장소나 인증 제공자 자체는 기본 검증 대상이 아닙니다.
Assure는 Mock과 효과 원장으로 실제 제품 로직이 올바른 요청을 저장·전송 직전
경계까지 전달했는지, 거부 입력에서는 요청이 발생하지 않았는지를 검증합니다.
내장 Adapter가 없는 외부 경계는 사용자의 LLM이 `.assure/adapters/`에
프로젝트 전용 Adapter를 생성합니다. Registry에 runner·대상 경계·파일
SHA-256을 기록하고 현재 Assure 생성기 표식을 넣어야 하며, 정적 검사와
Sandbox 건강검사를 모두 통과한 Adapter만 runner에 주입됩니다.

실행 중 테스트 환경, 어댑터, mock 또는 runner 자체의 실패가 확인되면 제품
실패로 판정하지 않습니다. 해당 시나리오는 미검증으로 분리하고 준비 문제와
제품 assertion 실패를 보고서에서 구분합니다. Assure가 만든 Firestore fake는
쓰기 후 읽기 상태가 이어지는 검증된 상태 저장 계약을 사용해야 하며, 오래된
무상태 fake는 기준선 검증 단계에서 거부됩니다.

Sandbox는 기능마다 새로 설계하지 않습니다. 프로젝트별 공통 Sandbox 프로필을
먼저 만들고, 모든 기능 probe가 동일한 격리·Mock·임시 데이터 계약을
사용합니다. 실행 전에 프로필의 환경 지문, 테스트 러너 기동, 네트워크 차단,
Mock 주입과 상태형 저장소 계약을 자체 점검합니다. 이 건강검사가 실패하면
제품 시나리오는 시작하지 않으며 결과를 제품 실패가 아닌 미검증으로 남깁니다.
테스트가 시작된 뒤에는 준비·생성·삭제·설치 승인을 다시 요청하지 않습니다.

모든 Assure 생성 테스트의 첫 부분에는 생성한 Assure 버전, 배포 소스
SHA-256, probe 스키마와 생성기 계약이 기록됩니다. 실행 전 현재 설치본과
모두 비교하며, 하나라도 없거나 다르면 해당 테스트는 절대 실행하지 않습니다.
과거 생성 테스트는 별도 질문 없이 강제 remap하여 `.assure/probes/` 아래에서
자동 삭제하고 현재 플러그인의 가이드로 다시 생성합니다. 프로젝트가 원래 소유한
테스트 파일은 참고 자료일 뿐이며 표식을 추가하거나 삭제하지 않습니다.

```text
// ASSURE_GENERATED: version=0.2.0-dev distribution_sha256=<sha256> probe_schema=2 generator_contract=assure-llm-probe-v2
```

최초이자 유일한 승인 요청은 프로젝트 기술 스택, test runner, 잠금 파일,
설치할 모든 의존성, 생성·교체할 `.assure/` 파일, 필요한 권한, 실행 명령,
정리 절차와 영향 범위를 모두 보여줍니다. 이 승인은 전체 Sandbox 조성과
모든 테스트 준비 절차를 허용합니다. 이후에는 결과가 나올 때까지 묻거나
멈추지 않습니다.

1. 프로젝트 구조와 테스트 환경을 조사합니다.
2. 프로젝트 공통 Sandbox 프로필과 필요한 준비 항목을 결정합니다.
3. 승인된 Sandbox를 조성하고 자체 건강검사를 통과시킵니다.
4. 기능별 사용자 시나리오를 구성하고 기존 테스트는 참고 자료로만 확인합니다.
5. 각 미검증 기능의 정상·실패·경계 입력과 기대 결과를 파악합니다.
6. 일괄 승인 범위 안에서 `.assure/` 파일과 기능 probe를 자동 생성합니다.
7. 위험한 외부 연결을 차단하고 호출 내역을 기록하도록 대체합니다.
8. 현재 source snapshot을 검증 기준으로 기록합니다.
9. 격리 권한과 임시 경로, runner를 사전 점검하고 일괄 승인된 준비를
   완료한 뒤 등록된 자동 검증 전체를 실행합니다.
10. 사람만 판단할 수 있는 항목과 미커버 항목을 함께 보고합니다.
11. 릴리스 판정을 반환합니다.

기능 probe 정책은 이름만 기록해 통과시킬 수 없습니다. Assure는 기준을
기준을 기록하거나 실행하기 전에 probe 파일과 제품 코드 진입점, 정상·실패·경계
사례, 결과·부작용 검증을 검사합니다. probe를 만들 수 없는 항목도 시도한
방법과 기술적 차단 사유가 있어야 하며, 그렇지 않으면 기준을 오래된
상태로 판정하고 다시 매핑합니다.

각 테스트의 `selector`는 Vitest·Jest의 `-t` 또는 pytest의 `-k`로 실제
실행 명령에 전달됩니다. 한 공용 probe 파일의 다른 테스트 실패를 해당
시나리오 실패로 기록하지 않습니다.

한 검증 항목의 사례는 정상·거부·권한·경계 순서로 실행하며 첫 실패에서
즉시 중단합니다. 이후 사례는 실행하지 않고 첫 실패의 테스트명, 메시지,
위치만 상세에 기록합니다. 다음 검증 항목은 계속 실행해 전체 기능 결과를
완성합니다.

운영 코드는 자동으로 수정하지 않습니다. 테스트가 기존 결함을 발견하면
수정 대신 검증 결과로 보고합니다.

## 결과 예시

```text
릴리스 판정: blocked

| 결과 | 개수 |
|---|---:|
| 통과 | 18 |
| 실패 | 1 |
| 확인 | 2 |
| 미검증 | 1 |

| 번호 | 위험도 | 영역 | ID | 검증 항목 | 방식 | 결과 | 상세 |
|---:|---|---|---|---|---|---|---|
| 1 | critical | 인증 | `authentication.login` | 올바른 정보로 로그인한다 | 자동 | 실패 | 종료 코드 1 |
| 2 | high | 화면 | `interface.visual-review` | 핵심 화면의 시각적 품질을 확인한다 | 수동 | 확인 | 담당자 확인 대기 |
```

각 시나리오는 다음 결과 중 하나를 가집니다.

| 결과 | 의미 |
|---|---|
| 통과 | 자동 검증 통과 또는 담당자의 수동 확인 완료 |
| 실패 | 검증 실패 |
| 확인 | 사람의 확인이 필요한 항목으로 아직 결과 대기 |
| 미검증 | 환경·권한·데이터·미커버로 판단 불가 |
| 제외 | 사유와 승인자를 기록하고 검증 대상에서 제외 |

자동 검증 실패의 상세에는 종료 코드만 표시하지 않습니다. 가능한 경우
오류 유형, 안정적인 오류 ID, 실패 테스트 이름, assertion 메시지, 발생
위치와 통과·실패 건수를 함께 기록합니다. 같은 오류 ID가 반복되면 동일한
공통 원인이 여러 시나리오에 영향을 주었는지 확인할 수 있습니다. 테스트
수집 전 환경 오류는 제품 실패가 아니라 `미검증`으로 구분합니다.

최종 판정은 시나리오 위험도와 미해결 증거에 따라 `releasable`,
`blocked`, `warning` 중 하나가 됩니다.

## 안전하게 실행되는 방식

Assure의 안전 원칙은 특정 외부 도구가 아니라 모든 실행 경로에
적용됩니다.

- 자동 검증은 Assure가 만든 임시 프로젝트 복사본에서 실행합니다.
- 원본 작업 트리에서 테스트를 실행하거나 운영 코드를 수정하지 않습니다.
- `.env`, 클라우드 자격증명, 비밀키를 복사하거나 상속하지 않습니다.
- 내부 임시 경로 쓰기·삭제와 외부 쓰기·네트워크 차단을 본 실행 전에
  preflight로 확인합니다.
- 잠금 파일 기반 의존성만 임시 복사본에 준비하며, 최초 Sandbox 일괄
  승인에 포함한 뒤 테스트 시작 전에 모두 설치합니다.
- package lifecycle script와 binary link를 비활성화합니다.
- 허용된 test runner와 인자 배열만 실행합니다.
- 테스트 실행 중 일반 네트워크 접근을 차단합니다.
- timeout 발생 시 하위 프로세스까지 종료합니다.
- 실행 후 Assure가 만든 임시 디렉터리만 정리합니다.

Docker 또는 Podman 데몬을 사용할 수 있으면 우선 사용합니다. 사용할 수
없으면 지원되는 OS 격리 provider를 통해 `local-isolated`로 동작합니다.
현재 내장 로컬 OS provider는 macOS `sandbox-exec`입니다. 컨테이너와 지원
OS provider가 모두 없으면 자동 테스트를 실행하지 않습니다.

외부 도구는 선택적 provider이며 Assure의 필수 실행 조건이 아닙니다.

### 안전 보증 수준

Assure는 네트워크 보증을 실제 격리 수준보다 강하게 표시하지 않습니다.

| 표시 | 의미 |
|---|---|
| `os-blocked` | Docker·Podman의 `network none`처럼 OS 또는 컨테이너 계층에서 외부 연결 차단 |
| `runtime-guarded` | runtime 방어만 적용된 상태로, 안전한 자동 실행에는 부족 |
| `not-run` | 자동 검증이 실행되지 않아 네트워크 보증도 적용되지 않음 |

현재 macOS `local-isolated`는 `sandbox-exec`로 파일 쓰기를 임시 복사본
안에 제한하고 네트워크를 차단하므로 `os-blocked`입니다. runtime 방어만
있는 `runtime-guarded` 상태에서는 자동 테스트를 실행하지 않습니다.

```text
기능 probe
├─ 제품 결과·상태 assertion
├─ 공통 effect ledger
│  ├─ 필요한 호출·쓰기·이벤트
│  └─ 금지된 호출·쓰기·이벤트
├─ runner adapter
│  ├─ Vitest: 내장 vi.mock·setup
│  ├─ Jest: 생성 Adapter + effect ledger
│  ├─ pytest: 생성 Adapter + effect ledger
│  └─ 기타: 지원 runner가 아니면 실행 거부
├─ runtime guard
│  ├─ 자격증명 제거
│  ├─ 별도 HOME
│  └─ HTTP·WebSocket·SDK 경계 차단
└─ 실행 provider
   ├─ Docker·Podman → os-blocked
   ├─ macOS local-isolated → os-blocked
   └─ 지원 OS 격리 없음 → 실행 거부
```

Assure가 외부 SDK 자체를 다시 구현하거나 검증하지는 않습니다. 사용자의
LLM이 발견한 요청·저장 경계에 최소 Adapter를 생성하고, 통제 입력과 effect
ledger로 제품 로직만 검증합니다. Adapter를 안전하게 만들 수 없는 경우에만
그 구체적 이유와 시도 내역을 `미검증`으로 보고합니다.

```text
외부 경계 발견
├─ 내장 Adapter 있음       → 자동 대체 + effect 기록
├─ 프로젝트별 Adapter 필요 → 사용자 LLM이 최소 Adapter 생성·검증
└─ 안전한 대체 불가능      → 실행 거부 + 미검증 근거 기록
```

## 보조 도구가 없어도 기능을 점검하는 방식

Assure는 Firebase, 자체 DB, OAuth, 사내 인증, 외부 API처럼 특정 기술에
맞춰 동작하지 않습니다. 기능 코드에서 입력 조건, 성공·실패 조건,
상태 변화와 외부 효과를 찾은 뒤 실제 코드 경로를 실행합니다.

예를 들어 로그인이 있는 시스템이라면 허용되는 값으로 인증 성공과 세션
생성을 확인하고, 잘못된 값이나 권한으로 인증 거부와 세션 미생성을
확인합니다. 데이터 저장 기능이라면 정상 입력이 한 번만 저장되고, 잘못된
입력이나 권한 없는 요청에서는 쓰기가 발생하지 않는지 확인합니다.

실제 운영 DB나 인증 서버에는 연결하지 않습니다. 격리된 실행에서 위험한
경계만 메모리 fake 또는 spy로 바꾸고 다음 두 가지를 함께 검증합니다.

- 사용자에게 보이는 결과와 상태 변화가 올바른가
- 필요한 외부 효과는 정확히 발생하고 금지된 효과는 발생하지 않았는가

Docker 같은 격리 보조 도구는 사용 가능할 때 안전성을 높일 수 있지만,
외부 서비스 Emulator나 실제 계정은 기본 기능 검증에 필요하지 않습니다.
보조 도구가 없어도 지원 OS 격리, Mock, effect ledger와 Assure 기능 probe로
동작합니다. 안전한 OS 격리 자체가 없으면 수동으로 돌리지 않고
`미검증`으로 보고합니다.

## 원하는 작업만 실행하기

검증 기준을 만들거나 업데이트하려면:

```text
이 프로젝트의 Assure verification map을 업데이트해줘.
```

승인된 최신 기준으로 다시 검증하려면:

```text
승인된 Assure 기준으로 전체 재검증해줘.
```

영문 요청도 사용할 수 있습니다.

```text
Run Assure for this project.
Update this project's Assure verification map.
Run the approved full verification baseline.
```

## 프로젝트에 생성되는 파일

```text
.assure/
├── sandbox-profile.json         # 프로젝트 공통 Sandbox 계약과 환경 지문
├── verification-manifest.yaml  # 기능, 시나리오, 위험도, 검증 기준
├── discovery-index.json        # 전체·증분 조사 inventory
├── adapters/                   # LLM 생성 Sandbox Adapter와 registry
├── probes/                     # Assure 소유의 프로젝트별 기능 점검
├── artifacts/                  # 자동 검증 증거
└── reports/                    # JSON 및 Markdown 결과
```

승인된 기준은 Git commit, deterministic source snapshot과 각 기능 probe
파일의 SHA-256을 함께 기록합니다.
제품이나 테스트가 변경되면 Assure가 오래된 기준을 감지하고 mapping부터
갱신합니다.

핵심 기준은 `.assure/verification-manifest.yaml`에, 조사 inventory는
`.assure/discovery-index.json`에 저장됩니다.

## 현재 제한 사항

- 아직 early beta이며 manifest 형식이 변경될 수 있습니다.
- 지원하지 않는 동적 구조는 미해결 범위로 남습니다. 프로젝트가 제공하는
  discovery adapter는 실행하지 않습니다.
- 컨테이너이 없는 로컬 자동 실행의 내장 OS 격리는 현재 macOS
  `sandbox-exec`만 지원합니다.
- 물리 기기 감각, 사람의 시각적 판단이나 동의, 법적으로 통제된 현실
  행위처럼 입력과 관찰 가능한 결과로 표현할 수 없는 항목은 수동 확인으로
  남습니다.
- 발견할 수 없는 제품 구조까지 완전한 coverage를 보장하지는 않습니다.
- 실패 진단과 운영 코드 수정은 검증과 분리된 작업입니다.
